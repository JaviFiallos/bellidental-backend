# 013 — Auditoría con Hibernate Envers (V16)

## Objetivo
Auditoría de cambios (RNF02, plan §4.9): quién cambió qué y cuándo en las tablas clínicas, de pagos, citas y
pacientes. Se usa Hibernate Envers; una consulta de solo lectura para ADMIN expone el historial de una fila.
`created_at/updated_at` siguen como están (no se tocan).

Depende de la 012 (`payments` y la entidad `Payment` deben existir). Nota: el export de la 018d (aún no ejecutada)
lee las tablas de `information_schema`, así que incluirá las `*_aud` sin cambios aquí.

## Criterios de aceptación
1. `application.yml` tiene `ddl-auto: validate`: **Hibernate valida también `revision_info` y las tablas `*_aud`
   contra las entidades al arrancar**. Cualquier `*IT` arranca el contexto; si falla con
   `Schema-validation: missing column [...] in table [..._aud]` o `wrong column type`, se corrige V16 (nunca se
   cambia `ddl-auto` ni se desactiva la validación).
2. **V16**:
   - `revision_info(revision_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, revision_at timestamptz NOT
     NULL, user_id uuid REFERENCES users(user_id))` (schema.dbml §11).
   - Para cada una de las 11 entidades, `<tabla>_aud` con: **una columna por cada campo mapeado de la entidad**
     (es lo que audita Envers; las relaciones `@ManyToOne/@OneToOne` aportan su columna `@JoinColumn`, p. ej.
     `patient_id`, `opened_by`), con el mismo tipo SQL que en la tabla original, **sin NOT NULL, DEFAULT, CHECK,
     FK ni UNIQUE**; más `rev bigint NOT NULL REFERENCES revision_info(revision_id)`, `revtype smallint` y
     `PRIMARY KEY (<columna id>, rev)`. Los tipos se copian de la migración que crea la tabla y de las que la
     alteran: V3 (patients), V5 (clinical_records, medical_history_entries), V6 (appointments), V7_1 + **V14_1**
     (encounters: añade `stomatognathic_regions smallint[]`, `diagnostic_exams varchar(20)[]`, `plan_description
     text` y **borra** `diagnostic_plan`, `therapeutic_plan`, `educational_plan`), V7_1 (encounter_diagnoses), V8
     (dental_findings), V9 (performed_treatments), V10 (prescriptions, prescription_items), V15 (payments).
     `char(1)` donde la entidad usa `bpchar`. Confirmar el nombre de cada tabla en su `@Table`.
   - Sin `REVOKE` ni triggers en las `_aud`.
3. `AuditRevision`: `@Entity @Table(name = "revision_info") @RevisionEntity(AuditRevisionListener.class)`,
   Lombok `@Getter @Setter @NoArgsConstructor`; campos
   `@Id @GeneratedValue(strategy = GenerationType.IDENTITY) @RevisionNumber @Column(name = "revision_id") Long id`,
   `@RevisionTimestamp @Column(name = "revision_at", nullable = false) Instant at`,
   `@Column(name = "user_id") UUID userId`. Si Hibernate rechaza `Instant` en `@RevisionTimestamp`, usar
   `java.util.Date` con `@Temporal(TemporalType.TIMESTAMP)` y anotarlo en Resultado (no cambiar la columna).
4. `AuditRevisionListener implements RevisionListener`, `newRevision(Object revisionEntity)`: toma
   `SecurityContextHolder.getContext().getAuthentication()`; si no es null y su `getPrincipal()` es
   `CurrentUser.CurrentUserPrincipal` → `userId = principal.userId()`; en cualquier otro caso `userId = null`.
   **No** usar el bean `CurrentUser` (lanza excepción sin usuario). El bot ya llega con el principal de
   `bot_whatsapp` (`BotApiKeyFilter`): no requiere código aparte; los jobs quedan con `null`.
5. Entidades: `@Audited` a nivel de clase. Las dos relaciones hacia entidades **no** auditadas llevan además
   `@Audited(targetAuditMode = RelationTargetAuditMode.NOT_AUDITED)` en el campo:
   `ClinicalRecord.openedBy` (`Professional`) y `MedicalHistoryEntry.condition` (`MedicalHistoryCondition`).
   (`ClinicalRecord.patient` y `MedicalHistoryEntry.clinicalRecord` apuntan a entidades auditadas: sin cambio.)
   Si Envers falla con los arrays de `Encounter` (`stomatognathicRegions`, `diagnosticExams`), poner `@NotAudited`
   en ese campo y quitar su columna de `encounters_aud`; anotarlo en Resultado.
6. `GET /api/v1/audit/{entity}/{id}` (`@PreAuthorize("hasRole('ADMIN')")`, `ApiResponse<List<AuditEntryResponse>>`).
   `entity` ∈ {`clinical-records`, `medical-history-entries`, `encounters`, `encounter-diagnoses`,
   `dental-findings`, `performed-treatments`, `prescriptions`, `prescription-items`, `payments`, `appointments`,
   `patients`} → `Map<String, Class<?>>` constante en `AuditService`; otro valor → 404 `ResourceNotFoundException`.
   `AuditService` (`@Transactional(readOnly = true)`, inyecta `EntityManager` y `UserRepository`):
   - consulta `AuditReaderFactory.get(entityManager).createQuery().forRevisionsOfEntity(clazz, false, true)
     .add(AuditEntity.id().eq(id)).addOrder(AuditEntity.revisionNumber().asc()).getResultList()`; cada fila es
     `Object[] {entidad, AuditRevision, RevisionType}`;
   - por cada revisión arma un `Map<String, String>` con los campos declarados de la clase (`getDeclaredFields()`,
     sin `static` ni `@NotAudited`, con `setAccessible(true)`), convirtiendo cada valor así: `null` → `null`;
     array → `Arrays.toString`; campo con `@ManyToOne`/`@OneToOne` → su id con
     `entityManager.getEntityManagerFactory().getPersistenceUnitUtil().getIdentifier(valor)` y luego
     `String.valueOf`; resto → `String.valueOf`;
   - `changes = AuditDiff.diff(mapaAnterior, mapaActual)` (en la primera revisión, mapa anterior vacío: todos los
     campos no nulos salen con `oldValue = null`);
   - `type` = `RevisionType.name()` (ADD/MOD/DEL), `at` = `revision.getAt()`, `userId`, `username` vía
     `userRepository.findById(userId)` (null si no hay usuario). Lista de la más antigua a la más reciente.
   Nunca se devuelven campos de `User` salvo `username`.
7. `AuditDiff` (puro): `static List<FieldChange> diff(Map<String, String> before, Map<String, String> after)` con
   `record FieldChange(String field, String oldValue, String newValue)` dentro de `AuditDiff`. Recorre la unión de
   claves, compara con `Objects.equals`, devuelve solo las que cambian, ordenadas por nombre de campo.
