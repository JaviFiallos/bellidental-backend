# 006a — Agenda: horarios y citas sin cruces

## Objetivo
Primera mitad del módulo `com.bellidental.appointments` (RF07; plan §4.3): migración V6, horarios de profesionales
(semanales y por fecha), creación de citas con cruce garantizado por la BD (`EXCLUDE`), estados, check-in y
reprogramación en recepción, vista de calendario y eventos de dominio.
Queda para la 006b: disponibilidad, walk-in y la interfaz pública `AppointmentScheduler`.

## Criterios de aceptación
**Migración V6** (columnas exactas de `docs/schema.dbml`: `professional_schedules` y §5 `appointments`; notas SQL al final)
1. `CREATE EXTENSION IF NOT EXISTS btree_gist;`
2. `professional_schedules`: id `bigint GENERATED BY DEFAULT AS IDENTITY`, FK a `professionals`;
   `CHECK ((weekday IS NULL) <> (specific_date IS NULL))`, `CHECK (weekday BETWEEN 1 AND 7)`,
   `CHECK (available = false OR (start_time IS NOT NULL AND end_time > start_time))`;
   índices `(professional_id, weekday)` y `(professional_id, specific_date)`.
3. `appointments`: `CHECK (status IN ('PENDING','CONFIRMED','ATTENDED','CANCELLED','NO_SHOW','RESCHEDULED'))`,
   `CHECK (source IN ('RECEPTION','PROFESSIONAL','BOT','WALK_IN'))`, `CHECK (end_at > start_at)`;
   FK a `patients`, a `users` (`created_by`), `rescheduled_from_id` UNIQUE → `appointments`,
   FK compuesta `(professional_id, specialty_id)` → `professional_specialties`;
   índices `(professional_id, start_at)`, `(patient_id, start_at)`, `(status)`;
   `CONSTRAINT appointments_no_overlap EXCLUDE USING gist (professional_id WITH =, tstzrange(start_at, end_at) WITH &&)
   WHERE (status NOT IN ('CANCELLED','NO_SHOW','RESCHEDULED'))`.

**Entidades y tiempo**
4. `Appointment`: `patientId`, `professionalId`, `specialtyId`, `createdBy`, `rescheduledFromId` como columnas simples
   (sin `@ManyToOne`); `status`/`source` con `@Enumerated(STRING)`; `OffsetDateTime` en `startAt`, `endAt`,
   `checkedInAt`, `createdAt`, `updatedAt`. `ProfessionalSchedule`: `weekday` `Short`, `specificDate` `LocalDate`,
   `startTime`/`endTime` `LocalTime`, `available`, `active`. Fechas de auditoría como en `Patient`.
5. `ClinicClock` (`@Component`): `zone()` (de `application.clinic.zone`), `now()` → `OffsetDateTime` en esa zona,
   `today()` → `LocalDate`. Usa el bean `Clock` de `ClockConfig` (`Clock.systemUTC()`), para fijar la hora en tests.

**Horarios** — lectura `PROFESSIONAL_READ`, escritura `SCHEDULE_MANAGE`
6. `GET /api/v1/professionals/{id}/schedules` → filas activas del profesional (`ScheduleResponse`: id, weekday,
   specificDate, startTime, endTime, available). Profesional inexistente → 404.
7. `GET /api/v1/professionals/{id}/schedules/effective?from=&to=` (fechas `LocalDate`; `to < from` o más de 31 días → 400)
   → lista de `EffectiveDayResponse`, un elemento por día, con sus turnos ordenados.
   `EffectiveScheduleResolver.resolve(LocalDate day, List<rows>)` → `List<Shift>`:
   - si hay filas activas con `specificDate = day`, solo se usan esas; si no, las activas con `weekday = day.getDayOfWeek().getValue()`;
   - si alguna de las filas elegidas tiene `available=false`, el día queda sin turnos;
   - si no, sus turnos ordenados por `startTime`.
8. `POST /api/v1/professionals/{id}/schedules` (201), `PUT /api/v1/schedules/{id}`, `POST /api/v1/schedules/{id}/deactivate`
   (`active=false`; nunca `DELETE`). Validaciones en `ScheduleService`:
   - exactamente uno de `weekday` (1–7) / `specificDate` → si no, 400;
   - `available=true` exige `startTime` y `endTime > startTime` → si no, 400;
   - turno que se solapa con otra fila activa y `available=true` del mismo profesional y mismo `weekday`
     (o misma `specificDate`) → 409. En PUT se excluye la propia fila.

**Citas** — permisos `APPOINTMENT_CREATE` / `APPOINTMENT_READ` / `APPOINTMENT_UPDATE` / `APPOINTMENT_CANCEL`
9. `POST /api/v1/appointments` (CREATE, 201). `CreateAppointmentRequest`: `patientId`, `professionalId`, `specialtyId`,
   `startAt` (obligatorios), `endAt`, `reason` (máx. 255), `notes`. En este orden:
   1. paciente: no existe → 404; inactivo → 409 (`PatientDirectory.findById`);
   2. especialidad: no existe o inactiva → 404 (`ProfessionalDirectory.findSpecialty`);
      profesional sin esa especialidad activa → 409 (`hasActiveSpecialty`);
   3. `startAt` antes de `ClinicClock.now()` → 400; `endAt` nulo → `startAt + defaultDurationMinutes`; `endAt <= startAt` → 400;
   4. `source` = `PROFESSIONAL` si `CurrentUser.professionalId()` existe, si no `RECEPTION`; `createdBy` = `CurrentUser.userId()`;
   5. si `source` es `RECEPTION` (o `BOT`, que llegará en 006b): la cita, convertida a la zona de la clínica, debe caer
      dentro de un único turno efectivo de su día (`EffectiveScheduleResolver`) → si no, 409 "fuera del horario".
      `PROFESSIONAL` está exento;
   6. `status = PENDING`; `appointmentRepository.saveAndFlush`. Si lanza `DataIntegrityViolationException` cuya causa
      (`org.hibernate.exception.ConstraintViolationException`) tiene `getConstraintName()` = `appointments_no_overlap`
      → `AppointmentOverlapException` ("APPOINTMENT_OVERLAP: el profesional ya tiene una cita en ese horario") → 409.
      Otras violaciones se relanzan. No comprobar el cruce en Java.
   7. publica `AppointmentEvent(id, CREATED, null)`.
10. Transiciones (`AppointmentTransitions`, métodos que reciben el estado y `checkedInAt` y lanzan `BusinessException`):
    | Acción | Desde | Resultado | Permiso | Endpoint |
    |---|---|---|---|---|
    | confirm | PENDING | CONFIRMED | UPDATE | `POST /appointments/{id}/confirm` |
    | cancel | PENDING, CONFIRMED | CANCELLED | CANCEL | `POST /appointments/{id}/cancel` |
    | check-in | PENDING, CONFIRMED sin check-in | `checkedInAt = now`, estado igual | UPDATE | `POST /appointments/{id}/check-in` |
    | no-show | PENDING, CONFIRMED sin check-in | NO_SHOW | UPDATE | `POST /appointments/{id}/no-show` |
    | reschedule | PENDING, CONFIRMED sin check-in | RESCHEDULED | UPDATE | `POST /appointments/{id}/reschedule` |
    | attend (lo usará 008) | PENDING, CONFIRMED con check-in | ATTENDED | — | sin endpoint |
    CANCELLED, NO_SHOW, RESCHEDULED y ATTENDED son finales. Cualquier otra combinación → 409.
    Cada cambio publica `AppointmentEvent` (cancel → CANCELLED; los demás → STATUS_CHANGED). Cita inexistente → 404.
11. `POST /api/v1/appointments/{id}/reschedule` (UPDATE, 201). `RescheduleAppointmentRequest`: `startAt` obligatorio;
    `endAt`, `professionalId`, `specialtyId` opcionales (por defecto, los de la original). En una sola transacción:
    validar la transición; original → `RESCHEDULED` y `saveAndFlush` **antes** de crear la nueva; crear la nueva con
    las mismas reglas del punto 9 (paciente, `reason` y `notes` de la original; `rescheduledFromId` = original);
    publicar `AppointmentEvent(nueva, RESCHEDULED, original)`. Si la nueva falla (cruce, horario), se revierte todo.
12. `GET /api/v1/appointments?professionalId=&from=&to=` (READ): `from`/`to` `OffsetDateTime`; `to <= from` o más de
    31 días → 400; `professionalId` opcional. Devuelve las citas que empiezan en el rango, ordenadas por `startAt`.
    `AppointmentResponse`: id, patientId, patientName, professionalId, professionalName, colorTag, specialtyId,
    specialtyName, startAt, endAt, status, source, reason, notes, checkedInAt, rescheduledFromId.
    Sin N+1: un `PatientDirectory.findByIds` para todos los pacientes y `ProfessionalDirectory.findActive()` una vez;
    especialidades vía `findSpecialty` cacheadas en un `Map` dentro de la petición.
    `GET /api/v1/appointments/{id}` (READ) → la misma respuesta para una cita; inexistente → 404.

**General**
13. Errores: 400 `InvalidInputException`, 404 `ResourceNotFoundException`, 409 `BusinessException` y su subclase.
14. No se tocan migraciones anteriores ni otros módulos fuera de las dos adiciones a los `Directory` listadas.

## Resultado
Se implementó completamente el módulo `com.bellidental.appointments` (horarios y citas) y se aplicaron todas las correcciones:
- **`domain/` puro**: Se creó `ScheduleRule` para evitar que `EffectiveScheduleResolver` dependa de entidades JPA.
- **Traducción del cruce**: Se ajustó `AppointmentService` para verificar la violación del constraint de PostgreSQL (`appointments_no_overlap`), soportando el caso real de la base de datos donde JDBC no retorna el nombre directamente para el constraint de exclusión.
- **Optimización**: Se agregó un caché interno en `getAppointments` (`computeIfAbsent`) para evitar N+1 al consultar las especialidades.
- **Refactorización**: Se centralizó la creación del response en un único `toResponse` y se eliminaron duplicaciones de lecturas de la base de datos.
- **Tests**: Se renombraron todos los tests al estándar `metodo_condicion_resultadoEsperado` (camelCase). Se agregaron los casos faltantes de `AppointmentServiceTest` y se dividió `AppointmentOverlapIT` en dos métodos separados con configuración de paciente (usando `PASAPORTE` para evitar duplicados en la base de datos).
- Se ejecutó exitosamente `./mvnw clean verify`. Surefire ejecutó todos los tests unitarios con éxito y Failsafe ejecutó 13 tests de integración (0 fallos, 0 errores).
